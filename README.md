# SRmesh @ Mininet

在 **WSL2 + Mininet** 上复现论文 *SRmesh: Deterministic and Efficient Diagnosis of
Latency Bottleneck Links in SRv6 Networks*（**ICNP 2025, CCF-B**）的核心设计。
全部跑在真实 Linux 数据面上（内核 SRv6 / IPv6 ECMP / netem）；
算法在本仓**独立实现**，不复用作者源码。

复现内容分三部分，均已完成：

- **Design 1 — 确定性 SR 环回探测**：用 SRv6 把探测包的**正向和反向路径都钉死**，
  把一个包的端到端 RTT 精确归因到指定路径。
- **Design 2 — 基于时延的多路径推断**：SR 的 SID 之间仍有 ECMP 歧义，用少量端到端
  观测反解每条链路的时延，定位瓶颈。
- **Design 3 — 拓扑无关的渐进式诊断**：三层剪枝的探测规划（模块度分区 + 渐进探测 +
  跨切片故障优先），把探测数压到 Pingmesh 全互联的 1/10 量级且不丢瓶颈可见性。
- **闭环集成**：三个 Design 接成一条闭环，在 8 节点**真实 SRv6 拓扑**上从规划一路跑到
  故障定位（`integration/`）。

## Design 1：确定性 SR 环回探测

核心思想：探测包用 SRv6 把**正向和反向路径都注好 SID**，让一个探测包只走一条
确定路径，从而把 RTT 精确归因到该路径。

```text
h1(发起) --正向 [r2_sid, r4_sid] 经 r2--► r4 -(End.DX6)-> h2(响应)
   ▲                                                      |
   +--反向 [r3_sid, r1_sid] 经 r3◄-- r1 ◄-(重建 SRH 回发)--+
```

1. **正向**：探测包用内核 `encap seg6` 走与生产流量同款的 SID 列表（探测 = 业务）。
2. **反向列表藏 payload**：反向 SID 列表写进 payload，不占第二个 SRH（规避 MTU）。
3. **响应端重建 SRH**：从 payload 取出反向列表，现场构造反向 SRH 原路回发。
4. **结果**：正向经 r2、反向经 r3，双向独立钉死。钻石拓扑各链路时延为正向
   1+2+2+1 = 6 ms、反向 1+20+20+1 = 42 ms，故 RTT 约 48 ms——两个方向被可测量地
   区分开。

### 两条实现路径

`design1/probe.py` 承载发起端与**用户态**响应端，`design1/responder.bpf.c` 是
**内核态**响应端。`design1/demo.py` 按开关选择路径：

```shell
design1/demo.py --ebpf   ->  design1/responder.bpf.c (内核态响应) + design1/probe.py probe-raw(发起)
design1/demo.py (默认)   ->  design1/probe.py respond (用户态响应) + design1/probe.py probe (发起)
```

`design1/probe.py` 的三个子命令：

| 子命令      | 角色                                   | 使用方             |
| ----------- | -------------------------------------- | ------------------ |
| `probe-raw` | 发起端（协议 253 原始套接字）          | `--ebpf` 模式      |
| `probe`     | 发起端（UDP）                          | 默认（用户态）模式 |
| `respond`   | 用户态响应端（AF_PACKET 重建反向 SRH） | 默认（用户态）模式 |

> 用户态路径（`probe` + `respond`）不依赖 eBPF 工具链（无需 bpftool/clang），
> 可独立验证「反向列表藏 payload + 重建 SRH」机制；内核态路径（`probe-raw` +
> eBPF）是论文的最终方案。

### payload 线格式

用户态与 eBPF 共用同一线格式（24 字节头 + 16×n），magic `0x53526D31`（"SRm1"），
网络字节序（探测端 `!I` 打包，eBPF 端用 `bpf_ntohl()` 读取）：

```text
magic(4) probe_id(4) seq(4) tx_ns(8) rev_cnt(1) pad(3) [rev_sid(16)]*n
```

## Design 2：基于时延的多路径推断

SR 把路径钉到 SID 粒度，但 SID 对之间仍有 ECMP。观测到端到端时延 d，却不知道
内部走了哪条分支，就无法把 d 拆到具体链路、定位瓶颈。Design 2 把「走了哪条分支」
当作未知量，用少量观测反解链路时延。

### 数据模型（`design2/infer.py`）

- **链路**：字符串 id（如 `x1`）。
- **观测**：`Observation(delay, segments)`，`segments` 每项为：
  - `('link', id)`：确定经过链路 id；
  - `('choice', [[ids], [ids], ...])`：歧义段，走其中一个分支。

### 算法阶段（`infer`）

1. **确定性消元**：对纯 `link` 观测（含已解析分支）做 NNLS，解出锚点链路时延。
2. **歧义解析**：对含 `choice` 的观测枚举所有分支组合，选误差最小者；若次优误差与
   最优之差不超过 `epsilon`（歧义阈值）则跳过。单未知链路可直接反解。
3. **迭代**：以上两步交替，直到不再变化。
4. **均值兜底**：仍未知的链路取已知链路均值。

### Mininet 端到端验证

- `design2/single_mininet.py`：拓扑 `S--M--Q--T`，r1→h2 按 flow hash 做 ECMP（直连 x2 或
  绕行 x3+x4）。确定性链路观测用点到点 ping 的 RTT/2；歧义观测用单向 UDP 时间戳，
  并用不同源地址触发不同 ECMP 分支。
- `design2/ambiguous_mininet.py`：两个 ECMP 点串联，h1→h2 理论 2×2 = 4 种路径组合，
  用 32 个单向样本聚成代表时延喂给推断算法。
- `design2/states_mininet.py`：链式三个 ECMP 点，锚点配置各不相同，一次运行同时覆盖
  Phase 2 的四种分支状态。

> 输入**只**包含测量值，不把样本的真实分支标签泄漏给算法：歧义观测统一表示为同一
> 条 `choice` 约束，分支归属完全由推断算法反解。

### Phase 2 分支状态（`infer(trace=...)`）

对一条含 ECMP 歧义的观测，Phase 2 对每个候选分支算 `(known_sum, unk, residual, err)`，
取 `err` 最小者；若次优与最优之差 ≤ `epsilon` 判为不可辨识。`infer` 的 `trace`
参数记录每次解析落在哪一类：

| 分支状态         | 判据                            | 是否产生新信息                 |
| ---------------- | ------------------------------- | ------------------------------ |
| A 全已知         | `unk = 0`                       | 否，幂等空转（仅确认分支归属） |
| C 单未知         | `unk = 1`                       | 是，反解该链路 = residual      |
| D 多未知         | `unk ≥ 2`                       | 部分，只能给“和”，不落具体链路 |
| B 两分支都无锚点 | 次优 err − 最优 err ≤ `epsilon` | 否，不可辨识，跳过             |

`design2/states_mininet.py` 三个 ECMP 点的锚点配置分别对应 A+C、D、B，一次运行即可
全部命中（终端与日志会打印覆盖报告）。

## Design 3：拓扑无关的渐进式诊断

Design 3 是**纯探测规划**：给定拓扑和一个切片（论文取
70% 节点），决定**探哪些节点对、按什么顺序探**。三层剪枝叠乘，目标是在不丢瓶颈可见性
的前提下，把探测数压到 Pingmesh 全互联（每对节点都探）的 1/10 量级。

### Step 1 分区探测（论文式 11 / Algorithm 2）

对切片子图做单层 Louvain 贪心模块度最大化（`plan.partition`）：初始每节点独立成区，
反复把节点移到让 ΔQ 最大的「相邻分区」，直到整轮没有任何移动。计划由三部分组成：

- **分区内全互联**：每个分区内所有节点对都探，路径**限制在分区诱导子图内**（对应论文
  里 SR-TE 把路径约束在分区内），这样分区内部的边才可能被覆盖；
- **代表节点跨分区全互联**：每个分区取分区内度数最大的节点当代表，代表之间再全互联；
- **覆盖补齐**：仍没被任何探测路径覆盖的边，用两端点直连补上，保证论文式 (6)
  「每条边至少落在一条探测路径上」。

### Step 2 渐进探测（Algorithm 3）

长路径正常 ⇒ 它包含的所有短路径都正常（论文 Fig. 8 的 A-D 正常 ⇒ A-B、B-D 都正常），
于是被正常路径包含的待探路径**直接免探**：

- 每轮只探「极大路径」（不被本轮待探集合里其他路径包含），批内按路径长度降序；
- 探到正常的路径，立刻把被它包含的路径从待探集合里删掉；
- **异常路径不产生任何免探**：它包含的短路径仍要探，才能把故障收敛到具体链路。

论文 Algorithm 3 的字面写法（第 4–8 行只在正常集 N 里查包含关系）在第一轮 N 为空时会把
所有待探路径都选进 S，退化成全量探测、拿不到论文正文声称的剪枝；本实现按**正文语义**
做（极大路径优先 + 正常路径的子路径免探），因此有剪枝且通常两轮收敛（实测平均 1.7–2.7 轮）。

### Step 3 跨切片故障优先

按论文的两条规则重排探测顺序：覆盖了**别的切片里已故障链路**的路径优先、覆盖了**还没被
别的切片探过链路**的路径优先；一旦**所有故障链路都已被某条异常路径覆盖就提前终止**。
跨切片故障传播按论文的 3% 概率模拟。

### 自测（`python3 design3/plan.py`，5/5 通过）

| 检查         | 内容                                                             |
| ------------ | ---------------------------------------------------------------- |
| 式 (11) 一致 | 直接求和 vs 增量 ΔQ 逐次比对，最大偏差 4.2e-17                   |
| 分区正确性   | 两个三角形 + 一条桥 → 恰好切成两个社区，Q = 0.3571               |
| 覆盖完备性   | 分区计划覆盖切片全部 10 条边，无遗漏                             |
| 渐进探测     | A→D 正常 ⇒ 其余 4 条免探（1 轮 1 条）；B-C 故障 ⇒ 两轮收敛到 B-C |
| 跨切片优先   | 命中「已故障 / 未探过」的路径排到最前                            |

链路级候选集由「所有异常路径的链路交集 − 所有正常路径的链路」得到（`plan.localize`）；
在「路径异常 ⇔ 含故障链路」的确定性模型下，实测候选集恰好收敛到被注入的那条链路
（`候选/故障 = 1.00x`）；有测量噪声时由 Design 2 反解。

## 闭环集成：三个 Design 一起跑

论文里 Design 1/2/3 本来就是一个系统。`integration/` 把它们接成一条闭环，跑在 8 节点
的**真实 SRv6 拓扑**上（不是模型）：

```text
Design 3 规划 (分区 / 计划 / 轮次)
   │  探测对 + 逐跳路径
   ▼
Design 1 执行 (逐跳 SID 列表 → encap seg6 → 响应端重建反向 SRH → 单向时延)
   │  每条路径的单向时延
   ▼
Design 2 反解 (nnls: 路径时延 → 链路时延, 阈值 E 判瓶颈)
   │  正常 / 异常 + 故障链路
   └──► 回到 Design 3 (渐进免探 / 跨切片优先 / 提前终止)
```

### 拓扑与寻址（`integration/srnet.py`）

两个三角形（a1-a2-a3、b1-b2-b3）+ 一条边（c1-c2）+ 三条桥（a1-b1、a2-b2、b3-c1）：
8 路由器 10 链路，模块度分区正好切成 3 个社区。每台路由器后挂一台**探测端点主机**
（a1h … c2h，链路不加时延），探针地址在主机上：

```text
a1h -- a1 --- a2 -- a2h         探测 = 主机到主机的 SR 环回
        \    /
         a3                     主机链路 0 ms ⇒ 单向时延 = 路由器链路时延之和
```

每个路由器一个 **node SID**（`End.DX6`：弹 SRH，把内层包交付给直连的端点主机）、每条
**有向邻接**一个邻接 SID（`End.X`：SL-- 后按邻接转发）；同一节点的 SID 都落在同一个
`/64` 里，所以每个节点只要一条聚合路由就能把外层包送到任意节点的 SID。探测按路径编译
SID 列表并**逐跳钉死**，反向列表照样藏在 payload 里由响应端重建——与 Design 1 完全同源，
只是从"固定 4 个 SID"变成"任意节点对、任意路径"。

> 端点 SID 必须用 `End.DX6` 交付给主机，不能用 `action End`（弹 SRH 后本地交付给路由器
> 自身地址）：实测本内核上 `End` 会把包原样弹回上游，探测直接超时。详见「关键坑」第 9 条。

### 三个阶段

| 阶段 | 做什么 | 为什么 |
| --- | --- | --- |
| 基线 | 全互联探一遍，Design 2 解出各链路时延 | Pingmesh 式常态基线，也是"异常"的参照 |
| 健康诊断 | 只跑 Design 3 的计划 + 渐进探测 | 单独衡量纯路径感知剪枝（Step 2） |
| 故障诊断 | 注故障后重探：渐进 → 候选集，Design 2 在候选集内反解超额时延 | 定位；Step 3 再加跨切片优先 + 提前终止 |

### 实测（`sudo python3 integration/closed_loop.py`，真实 SRv6 数据面）

8 路由器 + 8 端点主机，全互联 28 对，故障链路 b1-b3 两个方向各 +40 ms：

| 指标 | 结果 |
| --- | --- |
| Design 3 计划（Step 1） | 11 条（相对全互联 −60.7%），覆盖 10/10 条边 |
| Design 2 基线 | 28 条探测；设计矩阵秩 13/20 → 可唯一辨识 13 条链路，平均偏差 0.125 ms |
| 健康诊断（Step 2） | 8/11 条、1 轮（长路径正常 ⇒ 其余免探） |
| 故障诊断 | 11/11 条、3 轮（**异常路径不剪枝**），候选 = b1\|b3（正确） |
| Design 2 归因 | 候选链路超额 40.02 ms（netem 真值 40 ms） |
| Step 3 跨切片优先 | 1 条就让故障链路全部可见（提前终止） |

换成只被 1 条计划路径经过的链路（`--fault a2 b2`）时，故障诊断 8/11 条、1 轮收敛，
候选 = a2\|b2，Design 2 反解超额 39.90 ms——两种情形都一次命中。

三条值得注意的结论：

1. **秩只有 13/20**：即使全互联最短路探测，也有 7 条有向链路只能确定到"环路上的等量
   平移"——这正是论文里"SID 对之间仍有 ECMP 歧义"的线性代数形态，需要 Design 2 的
   歧义解析或更多锚点。
2. **故障下渐进剪枝收益取决于故障位置**：故障落在长路径上时异常路径不能剪掉它的子路径
   （11/11，要靠 Step 3 提前终止）；落在短路径上时仍有剪枝（8/11）。
3. **可见性 ≠ 可反解**：Design 3 保证每条故障链路都落在某条异常路径上；把它拆到具体
   链路靠 Design 2（在候选集内反解超额时延）。这和 `design3/eval.py` 的结论一致。

## 运行

```bash
# --- Design 1 ---
sudo python3 design1/demo.py --capture          # 用户态响应端
sudo python3 design1/demo.py --ebpf --capture   # 内核态 eBPF 响应端（需 bpftool + libbpf-dev + clang）

# --- Design 2 ---
python3 design2/infer.py                              # 算法自测 + 合成场景（无需 root）
sudo python3 design2/single_mininet.py --test         # 单 ECMP 点：Mininet + netem 真值
sudo python3 design2/ambiguous_mininet.py --test      # 两个 ECMP 点（4 种路径组合）
sudo python3 design2/states_mininet.py --test         # 三个 ECMP 点：覆盖 A/B/C/D 四种分支状态

# --- Design 3 ---
python3 design3/plan.py                               # 规划算法自测（式 11 / 覆盖 / 渐进 / 优先）
python3 design3/eval.py                               # 三层剪枝离线评测（合成拓扑，免 root）
python3 design3/eval.py --slices 256 --repeat 5 --faults 1   # 更大规模、更稳的均值
```

## 结果

### 算法层自测（`python3 design2/infer.py`，确定性、可复现）

| 场景                      |  MAE | 瓶颈定位 |
| ------------------------- | ---: | -------- |
| 论文数值例子（无噪）      | 0.00 | 检出 x2  |
| 菱形 ECMP（歧义指向瓶颈） | 1.25 | 检出 AT  |
| 菱形 ECMP + 噪声          | 2.00 | 检出 AT  |

内置自测：论文数值例子全部正确；歧义反解正确（观测偏离锚点 → 反解未知分支）；
不可辨识场景按预期走均值兜底（推断 5，真值 7，属设计内偏差）。

### Mininet 端到端（`logs/` 实测）

**单 ECMP 点**：MAE 0.069–0.119 ms；瓶颈 x2 正确检出。SRv6 定向观测实测
40.2–40.4 ms（理论 40 ms）。

**两个 ECMP 点**：9 条链路全部推断到真值附近，MAE ≈ 0.10 ms；瓶颈 x2 检出
（x6 = 20 ms 处于阈值边缘，属阈值选择问题）。

**分支状态覆盖**（`design2/states_mininet.py`）：一次运行命中 A/B/C/D 全部四种；
其中只有 C 会反解出未锚定链路（x3），D/B 信息不足，按设计走均值兜底。

> 说明：Mininet 场景里每条链路都有确定性观测直接测出，端到端 ECMP 样本主要用于
> **一致性校验**（验证歧义观测与已解链路自洽），而非在完全盲的条件下定位瓶颈。

### Design 3 三层剪枝消融（`python3 design3/eval.py`，合成拓扑）

4 个合成拓扑 × 256 切片 × 5 轮，切片取 70% 节点，每切片注入 1 条故障链路；「削减」

- **总体削减** 90.8–95.2%（平均 93.3%）与论文 91.9% 对齐；定性趋势也一致——模块度低的
  DC 拓扑收益最低。
- **Step 2 与 Step 3 的口径**：Step 2 在健康网络上衡量（纯路径感知剪枝），Step 3 才

## 环境

- WSL2，kernel 6.18，内核内置 SRv6（`IPV6_SEG6_LWTUNNEL=y` / `NET_CLS_BPF=y`）
- Mininet 2.3.0、iproute2 6.19、Python 3.14（`numpy` 2.4）、clang 21、bpftool 7.7
- 用户态路径与 `design2/infer.py` 仅需 Python 标准库 + numpy
- `design3/` 只用 Python 标准库（分区 / 最短路 / 渐进探测全部手写，不引入 networkx 等依赖）
- `integration/` 的真实拓扑需要 root（Mininet + `tc netem` + AF_PACKET）；`--simulate` 免 root

## 关键坑（复现必读）

1. 地址要 `nodad`，否则停在 `tentative`，IPv6 通信全废。
2. `seg6_enabled=1`，否则内核**静默丢弃**收到的 SRv6 包。
3. 端点 SID 用专用 node SID + `seg6local End.DX6`（不要拿接口链路地址当 SID）。
4. eBPF：`bpf_skb_adjust_room` 之后要**在每次迭代内做显式边界检查**，verifier 才可
   证；变长索引要用掩码夹进常量范围。
5. eBPF 读 payload 的 magic 用 `bpf_ntohl()`（探测端是大端 `!I` 打包）。
6. WSL2 上 `ping6 -F`（flow label）常无 `IPV6_FLOWLABEL_MGR` 权限，改用**多源地址**
   触发不同 ECMP hash。
7. 用 `ping` 的 RTT/2 做单向估计会被非对称回程污染，歧义观测改用
   `design2/oneway.py` 的单向时间戳。
8. **每条路径的每一跳都要先做 NDP 预热**：只预热正向会让反向路径的首个探测包在
   中途路由器上排队等 IPv6 邻居解析，首次 RTT 凭空多出约 80 ms（实测 129 ms vs
   稳态 49 ms）；`design1/demo.py` 因此对正向和反向逐跳各 ping 一次。
9. **端点 SID 要用 `End.DX6` 交付给主机，不能用 `action End`**：`action End`（弹 SRH
   后按内层目的地址本地交付）在实测内核上会把包原样弹回上游——接口计数显示 4 个包
   乒乓、响应端一个都收不到。改成"路由器后面挂一台端点主机 + `End.DX6 nh6 <主机>`"
   （这也是 demo.py 里验证过的形态）后立刻正常。闭环的 8 台主机就是为此加的。

## 已知局限

- WSL2 的 IPv6 ECMP hash 分布不均：两个 ECMP 点场景实测只出现 4 种组合中的 2 种
  （两个 ECMP 点倾向于同时选直连或同时选绕行），另外 2 种组合未被观测到。
- 端到端脚本仍依赖逐链路确定性观测；纯粹「只用端到端观测」的盲推断有待进一步验证。
- Design 1 的 eBPF 响应端仅支持最多 8 段（`MAX_SIDS`），且需外部注入 MAC/ifindex 配置。
- Design 3 的评测跑在**合成拓扑**上（18–20 节点），论文用的是 10 个 REPETITA 真实拓扑 ×
  4096 切片：合成切片小、社区偏多，代表节点全互联（C(k,2)）在 Step 1 的总量里占比高，
  所以 Step 1 削减比论文强；论文的 ILP 还额外约束跨分区的可见性，需要更多跨分区探测对。
  Step 2 比论文弱，则是合成切片的路径更短、路径包含关系不如真实拓扑丰富所致。
- 闭环集成只跑 8 路由器 + 8 端点主机的小拓扑：验证的是**机制**（SID 逐跳编译、单向时延、
  反向 SRH 重建、netem 故障注入、渐进剪枝、候选内归因），不是削减比例；论文的 91.9%
  削减看 `design3/eval.py` 的离线评测。小拓扑路径短（2–3 跳），Step 2 的包含关系少，
  健康诊断只从 11 条降到 8 条。
- 闭环里的"异常判定"用**相对基线的超额时延 + 固定阈值 E**；论文用历史基线 + 统计判定，
  本仓没做自适应阈值，也没有多切片并发（跨切片优先只用单切片内已故障链路模拟）。
- 闭环的响应端是用户态进程（每台端点主机一个，逐包重建 SRH）；eBPF 响应端只保留在
  Design 1 的单节点演示里，因为 `responder_cfg.h` 是编译期常量（每节点要单独编一份）。
